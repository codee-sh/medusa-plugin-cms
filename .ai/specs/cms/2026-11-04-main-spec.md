# CMS (Content Collections on Medusa Models)

**Date:** 2026-11-04
**Status:** review
**Area:** backend | admin

> Folder: `.ai/specs/cms/`

## TLDR

Editors of a Medusa store need to change content - pages, their sections, a blog - without a developer.
Medusa has no content model of its own, so each project builds one content type at a time, each with its
own module, workflows, routes and Admin screens.

`@mostrajs/cms` is a **CMS as a Medusa plugin**, released as open source. Content
is stored in **ordinary Medusa models** that the host project writes in its own module: one model per
collection (`content_page`), one per block type (`content_block_hero`), every piece of content in its own
column, and one **area** model (`content_area`) that ties a document's sections to their blocks with
foreign keys and cascades. Every collection is registered the same way in a CMS config; the plugin reads
the models' DML schema and supplies everything else: generic workflows, Admin and store API, the Admin
**Content** screens, validation, publishing and cache handling. The store API reads like Medusa's own:
`fields`, `order` and declared filters. Any storefront reads it its own way.

**Why (user, 2026-11-16).** A store built on Medusa needs a CMS too, and today it gets one beside it: a
second backend and database (a headless CMS, self-hosted or a paid service), a second admin with its
own accounts, roles, translations and preview, a second API for the storefront, and a sync of product
ids between the two. Medusa ships no page management in its admin, while hosted commerce platforms
build theirs in. This plugin makes content work the way commerce already does in Medusa - the
same database, the same Admin under **Content**, the same workflows, users and roles, Translation
Module, file provider, and a store API in Medusa's style - so a client runs one system and an agency one
stack. It covers a store's content: pages and landing pages of sections, content bound to products and
categories (D35), static pages, a blog, menus (D34). Live preview, visual editing, editorial approval
and portals built around content come when a project asks for them.

> Pages, landing pages and a blog managed in the Medusa Admin, stored in your own Medusa models, written
> through Medusa workflows and read through a store API like Medusa's own: one database, one admin, one
> way of working for commerce and content.

The concepts are those of an established CMS; the storage keeps its foreign keys but not its table
count.

**Host project.** The Medusa application that installs the plugin and writes the content models. Its own
models, config, links and storefront integration are specified in its repository, not here. Integration
tests of the plugin need a host project's models and database, so they run there.

## Decisions Taken

- **D1. Open source, built on real use (user, 2026-11-04).** The plugin is MIT licensed and generic. Its
  first content model - pages made of blocks, a blog with categories and tags - comes from a real
  project and drives the phases, but the plugin names none of it.
- **D2. Content models are ordinary Medusa models (user, 2026-11-04).** The host project writes its
  content types the way Medusa prescribes: a module with DML models, a service, migrations from
  `npx medusa db:generate <module>`. The CMS generates no model and owns no migration of the project's.
  Ids, indexes and module names are the project's choice. Medusa ties a model's key in the service to
  its DML name: `content_page` is the key `ContentPage`.
- **D3. Content lives in columns, never in a JSON blob (user, 2026-11-04).** Every text, number, date,
  option or reference of a document or block is a column, because Medusa's Translation module translates
  only `model.text().translatable()` properties (`packages/core/utils/src/dml/properties/text.ts:80`,
  since 2.13) and Medusa's filters and `.searchable()` work on columns. `model.json()` columns are not
  editable through the CMS, with one exception: `metadata`, which holds presentation settings and no
  content (2026-11-07, user).
- **D4. Blocks hang off an area model with foreign keys (variant B, user, 2026-11-04).**
  - Each block type is a model with one `belongsTo` named `area` to the project's area model
    (`area_id`) and a `rank` column. A repeatable list inside a block is a child model with `belongsTo` to the block and a
    `rank` column.
  - The area model (`content_area`, with `name` and `parent_id`) has one nullable `belongsTo` per
    collection that has areas, a `CHECK` that exactly one is set, one `hasMany` per block type, and
    `.cascades()` over its blocks. Each collection has `areas: hasMany(Area)` with a cascade. The names
    `areas` and `area` are fixed, as the plugin's column names are, so the registry finds the area model
    through them (user, 2026-11-10).
  - Result: foreign keys from every row up to its document, Medusa's soft-delete cascade down the whole
    chain, one `query.graph` per document read, filters across the relations, and two places to touch
    when a collection or a block type is added - the new model and the area model.
  - Alternatives weighed with the user: relations from every block to every collection (variant A: no
    extra table, but an edit in every block for each new collection and in every collection for each new
    block) and polymorphic owner columns on the blocks (variant C: no extra table, no edits, no foreign
    keys - the Translation module's `reference` / `reference_id` pattern). B was chosen for
    database-enforced integrity at the cost of one small table.
- **D5. Block storage is plain functions (user, 2026-11-08).** Reading a document's areas and preparing a
  save are plain functions of the plugin (`buildDocumentAreas`, `prepareDocumentWrite`), with no storage interface;
  the save is applied by one write step per kind of call, each with its own compensation (user,
  2026-11-09). The first design put them behind an interface so that a
  later switch to variant C stayed possible; D26 removed the reason, and an interface with one
  implementation is code to maintain for nothing.
- **D6. Registration in config, introspection for the rest (user, 2026-11-04).** The host project's
  config registers collections and blocks by DML model, all in the one module it names, passed to the
  plugin as its `options` (the model replaced the entity name on 2026-11-08, user: a module service read
  inside a workflow step hides its class statics, so the models cannot come from the service). The plugin reads each model's DML schema (`Model.parse()`, `property.parse()`:
  type, nullable, enum choices, relations) and derives the Admin field, the validation and the API shape.
  The config states only what DML cannot say: labels, which text column is a slug, which `_id` column is
  a media field or a commerce reference, publish-required fields, which block types each area accepts,
  the options of an options field (D18) and the fields a store request may filter on (D20). The area
  model is not among them: DML says it, as the target of the `areas` and `area`
  relations (D4; user, 2026-11-10). What the Admin needs is plain data; a field's `serverValidation` and
  a slug's `serverTransform` are functions that stay in the backend, and code the Admin runs - an options
  hook - is named in the config and registered in the host's Admin (D18, D33). The Admin never reads the config
  itself, only the projection `GET /admin/cms/collections` builds from it.
- **D7. Document state is model properties (user, 2026-11-04).** A collection model has columns of its
  own, checked by the registry: `status` (`draft` | `published`), `published_at`, `created_by`,
  `updated_by`.
- **D8. The published state lives on the row.** Until versions ship (D13), saving a published document
  changes live content at once. Versions come right after sub-phase 1a (D22), so this holds only for
  the documents saved between 1a and them.
- **D9. References.**
  - A `belongsTo` or `manyToMany` from a collection to another **registered collection** (a blog post's
    categories and tags) is a relation the Admin edits with a picker and the store API returns populated
    one level, published documents only. The Admin and the projection carry it as ids under
    `<relation>_id` / `<singular relation>_ids` (`category_id`, `category_ids`, `tag_ids`), the naming
    Medusa's product module uses; the store API returns the documents under the relation's name
    (`categories`, `tags`), the same rule as media fields.
  - Only the owning side is a field: the `belongsTo`, or the `manyToMany` side with `pivotTable`. The
    other side (`posts` on a category) exists because DML requires it and is structure, never edited or
    returned.
  - The default picker searches the target collection by its `useAsTitle`. A relation may instead carry
    `options`, the same field type as D18, for a short or narrowed list with its own labels.
  - A media field is a text column marked in the config, holding what the media provider stores for a
    file (D29), and its record comes from that provider. The read-only module link per column that this
    bullet first prescribed is replaced by D29 (user, 2026-11-10).
  - A commerce entity (product, category, product collection) is an `_id` column marked in the config and
    stays an id: populating it would bypass the visibility its own routes apply.
- **D10. Lists carry no blocks by default.** A store list returns documents without their areas, and a
  single document, by id or by slug, with all of them. Either reaches the areas `fields` names (D20), one
  by one: a list of products' documents asks for `*teaser`, a page found by a filter for `*sections`,
  in one request. A list that names an area takes at most 50 documents; listing a blog
  without areas never reads block tables (user, 2026-11-16).
- **D11. Names.** Plugin routes `/admin/cms/...` and `/store/cms/...`, Admin route `/app/cms`, label
  **Content**, collection slugs from the config. Medusa owns "collection" (product collections,
  `/admin/collections`); the CMS uses the word only under `/cms`. Id prefixes must be unique across the
  registered models: the Caching Module recognises an entity by its prefix. Responses use the models' own
  column names, snake_case.
- **D12. Permissions are deferred (user, 2026-11-04).** No RBAC policies in the first versions: every CMS
  Admin route is open to every authenticated admin. Intended shape, for `sub-cms-permissions`: one
  resource per collection, `cms_<slug>`, with `read`, `create`, `update`, `delete`, `publish`. Each
  collection has its own path prefix, so policies can be added without a contract change.
- **D13. Versions go to one plugin table, later.** `cms_version` (`collection`, `document_id`, `version`,
  `snapshot`, `status`, `latest`, `created_by`), a full snapshot per version (user, 2026-11-06), a
  static model of the plugin with its own migration. A snapshot is history, not live content, so JSON
  there does not contradict D3.
- **D14. One validation schema from the client projection.** A pure builder turns a collection's
  projection (introspected fields plus config) into a Zod schema that collects every error with its path.
  It takes `z` as an argument, so the backend passes `@medusajs/framework/zod` and the Admin its own Zod,
  and the file imports nothing from Node or the framework: the Admin bundle cannot load Node modules.
- **D15. The first versions run on Medusa 2.21.** What 2.22.x adds for the CMS is permission tooling -
  route `permissions` (`@medusajs/admin-sdk` `config/types.ts:72-86`), the dashboard permission hooks,
  `authorize` - none in 2.21.2, so moving the peer range is weighed with `sub-cms-permissions`. 2.22.0
  also requires Node 22.22+ and boots only with a `MEDUSA_LICENSE_KEY` covering `rbac`.
- **D16. Its own repository, developed through yalc (user, 2026-11-06).** The plugin is
  `@mostrajs/cms`, in its own repository, built with `medusa plugin:build`.
  - It owns no table until versions (D13); its small `cms` module only holds the config from its
    options. It imports nothing from a host project and reaches the project's models through the
    container.
  - While unpublished, a host project reaches it through Medusa's local plugin flow: `medusa
plugin:publish`, `plugin:add` and `plugin:develop`, which run on yalc.
  - Publication to npm is a step of its own, on the maintainer's decision.
- **D17. The CMS is independent of any storefront (user, 2026-11-04).** The store API is a generic,
  documented contract; it carries no storefront's component names or mapping. A storefront's integration
  belongs to its own project.
- **D18. Option fields with project-supplied values (user, 2026-11-05; reworked 2026-11-12).**
  - A field type says how the options are picked: `select`, a dropdown of the few options its config
    lists, on a text or an enum column; `combobox`, searched as the editor types, on a text column, or with
    `multiple: true` several values on an array column; `checkboxes`, every option shown at once, on an
    array column, for short lists.
  - `options` is a `{ value, label }[]` list or, on a `combobox` or `checkboxes`, `{ hook: "<name>" }`: a
    React hook the host registers under that name in its own Admin
    ([sub-admin-extension-registry](./ended/2026-11-12-sub-admin-extension-registry.md)), which fetches the
    options in the browser from any source - Medusa's API, the project's routes, a constant - and maps
    the data to options itself. The CMS adds no options route and proxies nothing.
  - A listed set is checked on a write; a hook's values are checked as texts only, as the server never
    sees the hook's source. The store API returns the stored values and, when the field is `filterable`
    (D20), filters on them.
  - The plugin gives the values no meaning. Whether a value hides content - a market on a page - is the
    storefront's decision (D17), so the store API stays public.
  - Rejected (user, 2026-11-12): options as a function of the Medusa container resolved on the server (no
    search, no pages, run on every projection), `GET /admin/cms/references/:target` (the CMS a proxy of
    every source), `type: "options"` with an `input` (a type per behaviour reads the same as the other
    field types), `multiselect` (a combobox of several values).
- **D19. One shape for every content type (user, 2026-11-06).** Collections and blocks share one core:
  `slug`, `model`, `labels`, `fields`; the config names their one `module`. A collection adds `admin`, `store`,
  `drafts`, `areas`; a block adds `repeaters` (D32). Block types are declared once and a collection
  picks them through `areas`. A key of `fields` is a column or a relation's id key, and says whether the
  field is required always or at publish (sub-spec, 2026-11-09), so a
  relation is configured like any other field. `drafts: false` makes a dictionary collection (categories,
  tags) published from its creation, with no Publish step.
  - Amended 2026-11-24 (user): drafts are opt-in, `drafts: true`.
    A collection without the key is live from its creation, as most of a host's collections - settings,
    dictionaries, a market's homepage - need no Publish step; a singleton and a drawer-edited collection
    refuse `drafts: true` rather than need `drafts: false`.
- **D20. Store reads follow Medusa's query conventions (user, 2026-11-06).**
  - `fields` has the syntax of Medusa's API and SDK: `title,slug` replaces the defaults, `+x` adds, `-x`
    removes, `*rel` or `rel.*` selects a whole relation, `rel.name` one field of it. A field that is not
    public, or deeper than one level (D9), is left out without an error, as Medusa does. `order` is the
    same, defaulting to `-published_at`. The plugin parses both with Medusa's `validateAndTransformQuery`,
    given the schema and query config the registry builds per collection, as both depend on the config
    (user, 2026-11-17); the routes read `req.queryConfig` and `req.filterableFields` as Medusa's do.
  - Access is the project's (user, 2026-11-17): the store API checks no customer, and a project's
    middleware on `/store/cms/*`, which Medusa runs before the plugin's, may require one or force a
    filter; the plugin reads the query only after it.
  - What a client can select is a closed list, like Medusa's strict `allowed` (2.21.0): the public
    columns and relations, each media field with its record whole (D29), and what the project
    opens with Medusa's `allowFields`. A field is public unless its config says `store: { hidden: true }`,
    in a collection or a block; the plugin derives `allowed` from the fields and never takes it from the
    config, so what a field shows in the store is said beside the field (user, 2026-11-18). A path that
    is no field of the config, such as a project's own link, the project opens with `allowFields`. An area and its blocks are selected as Medusa selects
    nested relations, by a path of the area, the block type and the field, through repeaters to
    `maxDepth`: `*sections` the whole area, `sections.hero.*` its hero blocks, `sections.hero.title` one
    field of them, `sections.grid.items.grid_item.title` one field inside a repeater (user, 2026-11-18,
    replacing "an area is selected whole"). A block always comes with its `id` and `block_type`, in
    `rank` order, and a block type the selection does not name is left out. The paths are part of
    `allowed`, which the registry derives, so the read loads only the block types and fields named.
  - Filters are opt-in: `store: { filterable: true }` on a field makes it a query parameter of the
    collection's list; any other parameter answers 400. There is no separate route for a flag or a lookup.
  - **The Store API's config has Medusa's shape (user, 2026-11-18).** A field's `store` holds what the
    field does in the Store API (`hidden`, `filterable`), as its `admin` holds what it does in the Admin
    (D33). A collection's `store` is `false`, which keeps it out of the store, or `{ list?, retrieve? }`,
    each a part of Medusa's `QueryConfig` - `defaults`, `defaultLimit`, `storeRelationsLimit` - as
    Medusa's own `listProductQueryConfig` and `retrieveProductQueryConfig` are; left out, a list
    defaults to every public field but the areas, and a single document to every public field with
    them.
  - Three deliberate differences from Medusa: an area's path names the area and the block type, not
    the block relations, because those are storage detail; a list that names an area takes at most 50
    documents (D10); a commerce reference stays an id (D9).
- **D21. Withdrawn: exclusive flags and scopes (user, 2026-11-18).** A boolean `type: "exclusive"` held
  by one published document per cell of its `scope` fields, such as a page's `is_homepage`, and values
  unique per cell of a compound unique index, were dropped before release: a homepage taken from another
  page at a publish, cells with a default value and a most-specific pick are rules an editor cannot see.
  A unique value, a slug included, is unique in its collection. Which page is a homepage is to be held by
  a collection's settings, specified next. The number is kept so the decisions after it keep theirs.
- **D22. Delivery in numbered versions (user, 2026-11-06).** Plugin versions are the milestones: 0.0.1 is
  `sub-collections-and-documents`, 0.0.2 `sub-versions-and-drafts`, 0.0.3 `sub-draft-read`, 0.0.4
  `sub-cms-translations`. A version is finished when its sub-spec's phases are done and verified in a host
  project; it says nothing about publication (D16). Work order (user, 2026-11-09): `sub-versions-and-drafts`
  is built right after sub-phase 1a of `sub-collections-and-documents` and before its blocks (1c), so
  blocks, lists and nesting are written into versions from the start rather than added to them later;
  0.0.1 is finished only with its last sub-phase, so 0.0.2 is finished before it.
- **D23. Plain `MedusaService`, Medusa's compensation (user, 2026-11-06).** The host project's module
  extends `MedusaService` like any other, and a save calls its generated methods from a workflow step,
  each its own transaction. A failed write answers `StepResponse.permanentFailure` with what was written,
  and the step's compensation undoes it, as for any later failure. One transaction through a plugin base
  class was dropped: more code and a module unlike the others, for a failure that another save repairs.
- **D24. Pages are the base (user, 2026-11-06).** 0.0.1 starts with one collection, `page`, and every
  mechanism a collection needs. The plugin names no collection, so each later collection is a model and a
  config entry. Each sub-phase ends in something that runs.
- **D25. Rich text is a field type, stored as Lexical JSON in a text column (user, 2026-11-07).**
  `fields: { body: { type: "richtext" } }` works on any `model.text()` column, with no model change. The
  Admin edits it with Lexical; the column holds the editor's document as a JSON string, because
  translations cover `text` columns only (D3). The store API returns the document as an object and each
  storefront renders its nodes (D17), so no HTML is stored or served.
  - Rejected: `model.json()`, which cannot be translated and breaks D3; HTML in a `text`
    column, which is the simplest to render but must be sanitised and gives no control of its structure.
  - A `richtext` column is not `searchable`: a search would match the document's node names.
  - Amended 2026-11-17 (user): what the editor offers is named **features**, defaults under the config's
    `richText` and a field's own `features` replacing or extending them; the server checks a document
    against its field's features. Translations are edited in the plugin's Admin, as Medusa's screen would
    show the JSON. Detail in [sub-rich-text](./2026-11-17-sub-rich-text.md).
  - Amended 2026-11-20 (user): a feature carries its options - the plugin's factories, such as
    `HeadingFeature({ enabledHeadingSizes })` and `LinkFeature({ linkPolicy })`, return plain data under
    the common CMS keys; `headings` and a field's `linkPolicy` move into their features, and of two
    features with one key the last wins. Detail in
    [sub-rich-text-features](./ended/2026-11-20-sub-rich-text-features.md).
- **D26. Areas are flat and nest through `parent_id` (user, 2026-11-07).** Any block can hold
  areas - its `repeaters` (D32) - in any combination, through the config, with no model change. Every area, at any
  depth, keeps its foreign key to the document, and `content_area.parent_id` names the block it
  sits in, `null` at the top. Cascades stay document -> areas -> blocks, one read loads every level, and
  the tree is built in memory.
  - The place is an id, not a path, so ids survive a reorder, and blocks need no new column.
  - Rejected: a foreign key from the area to the row, because a cycle of cascades makes every soft delete
    throw (`detectCircularDependency`) and each new holder would add a column; a `path` column on every
    block, which is one column per model and is rewritten by every move.
  - `parent_id` has no foreign key, as it can name any table, but unlike variant C (D4) the lifetime of
    every row still hangs on foreign keys up to the document. Deleting a block deletes the areas under
    it in the plugin.
  - `maxDepth` (default 4) bounds the data, so a block may be allowed inside itself.
- **D27. A save writes everything it is sent (user, 2026-11-08).** A save updates every document and
  block it carries, at any depth, with all their values, creates the ones that are new, and soft-deletes the
  stored ones it no longer carries. It does not compare values to find what changed. Generated methods
  take arrays, so a save is one call per model and operation, not one per row.
  - Rejected: a diff of each row's values (more code for fewer written columns, which nothing needs at
    ~20 blocks), and deleting the whole tree and inserting it again (twice the writes,
    and a moment where the document has no blocks, because the two calls cannot share a transaction).
- **D28. The form shows only the fields the config lists, in its order (user, 2026-11-10).** A model's
  `fields` in the config are its form: a column not listed is no field, so the Admin does not show it and
  a write refuses it, and the fields keep the config's order. The registry refuses a listed name that is
  not a column, a system or CMS column, `metadata`, a column of a kind the Admin does not edit, and a
  column the model requires that the config leaves out, as no write could fill it. `hidden` is gone.
  Nothing about a field is read from the model either: each field states its `type` and `label`, a
  column the database requires states `required: "always"`, and a select lists its `options` as
  `{ value, label }` on a text column; the model is only checked against them - the type fits the
  column, and on an enum column the options fit its values (user, 2026-11-10). Every listed field is
  public in the store API unless it says `store: { hidden: true }` (D20, user, 2026-11-18).
  - Rejected: every column a field unless `hidden: true` (a new column reaches the editor unasked, and
    the form follows the model's column order); a type, a requirement or choices inferred from the
    column (the config would not say what the form does).
- **D29. Media through a media provider, over Medusa's File Module (user, 2026-11-10).** Replaces the
  read-only links of D9.
  - Two layers. Where a file is stored is Medusa's: the File Module with its file provider (S3, local),
    set up in the host project's `medusa-config.ts` as usual. The plugin has no storage option. On top
    of it sits the plugin's **media provider**, which says how a file is uploaded, how a record is read
    and whether it can be searched.
  - A media provider is a class extending `AbstractCmsMediaProvider`, exported by the plugin and
    modelled on Medusa's providers: a constructor `(container, options)`, `static identifier`,
    `static validateOptions(options)` and a `maxFileSize` getter, the largest upload its options allow,
    which the upload route and the Admin ask an instance for. Its methods are `retrieve`, `upload`, `delete` and an
    optional `list`. The CMS calls them from its steps and checks, places and limits what they answer; a
    provider only talks to its source - the File Module, or the module of another plugin or of the
    project.
  - The config names it as `media: { provider: { resolve: ProviderClass, options } }`, `resolve` being
    the imported class. There is no implicit default: without `media.provider` a config cannot have a
    media field. The plugin creates the instance inside the step that uses it, with that step's
    container, so a provider resolves modules as a step does. A provider cannot be a module provider of
    the CMS module, loaded once into its container as Medusa loads the File Module's: modules are
    isolated, and a provider reaches other modules.
  - The plugin ships `FileMediaProvider`, which a host project imports and names to work with Medusa
    alone: `createFiles`, `retrieveFile` and `deleteFiles` of the File Module, answering what they
    answer, and no `list`, because the File Module lists files by id only. A host project with a media
    library of its own, such as an asset module with renditions and search, writes its own provider over
    it, with `list`, and names it instead; that module still stores its files through the File Module.
  - The first version ships `FileMediaProvider` only; a provider over the first host project's asset
    module comes later, as its own step (user, 2026-11-10).
  - **One file or several, by the column** (user, 2026-11-10): a media field holds one file on a text
    column, or several on an `array` column (`model.array()`) with `multiple: true` in the config, which
    grants the right to upload several, in the array's order, up to an optional `max`. The CMS keeps no
    table of its own, neither of media nor of links between content and media.
    - Rejected: a links table in the CMS (`<owner>, field, value, rank`), whose point would be a foreign
      key to a media collection, which a provider's records cannot have; a media
      library in the plugin, which would duplicate a host project's asset module. A media library as a
      plugin of its own may come later, behind the provider.
  - **The config says what a media field stores** (user, 2026-11-10): `stores: "id" | "url"` puts the
    record's id or URL in the column. A provider lists what it can read back (`static stores`), and the
    registry refuses a field it cannot serve.
  - **A read returns the record in place of the value**, under the column's own name
    (user, 2026-11-10): the column keeps its text (or array of texts), a write sends that text, and a
    read answers the record (or the records, in order) built by `retrieve` at read time. Nothing about
    the record is stored. A column named `image` reads as `image.url`.
    - Rejected: the record next to the value under a key of its own (`as` in the config, or the column's
      name without `_id`), which needs a second name per field and a registry check against collisions.
  - A record is `CmsMedia`: `id` and `url` always, `filename`, `mime_type`, `size` and `thumbnail_url`
    when the provider knows them, and whatever else the provider adds. The File Module answers
    `{ id, url }` only, so the Admin works from those two: the name from the URL's last segment, the URL
    as the thumbnail.
  - What a provider answers is what its backend answers, and the store API returns the record whole, so
    the provider decides what is public; `fields` selects a media key but not paths inside it (user,
    2026-11-10). On S3, `FileMediaProvider` answers a signed URL valid for an hour, as Medusa's own
    `retrieveFile` does; the README says so, and a project that needs lasting URLs names a provider that
    stores them.
  - The plugin reads media through `retrieve`, once per read and kind of value with the values of every
    media field the read holds, document and blocks alike, and does not cache them; a provider caches
    its own (user, 2026-11-10). A host project's read-only links for media fields are removed.
  - The Admin's picker uploads and, when the provider has `list`, searches. It deletes nothing: removing
    an image clears the field. `delete` only compensates an upload whose workflow failed after it.
  - The picker, its library modal and its drop zone are the plugin's own components, started from the
    first host project's asset library, as ManagerFields was; the host project keeps its own for its
    other screens.
  - Rejected: a read-only link per media field (the first D9). One link file per column in the host
    project, the plugin tied to one module's record through `media.entity` and `allowedFields`, and no
    way for the plugin to upload.
- **D30. Fields render one by one, through `ManagerFormFields` (user, 2026-11-11).** `ManagerFields`
  becomes `ManagerFormFields`: one set of generic fields shared by the plugins and projects that build
  forms, rebuilt in this plugin first and ported to the others later.
  - It stays on react-hook-form, which the dashboard itself uses, and renders each field through the
    dashboard's `Form` parts: `Form.Field`, `Form.Item`, `Form.Label` (with `optional`), `Form.Hint`,
    `Form.Control` and `Form.ErrorMessage`. A field of its own and a `Form.Field` of the form's own
    look the same, and a form using it sits inside the dashboard's `Form` or a route modal's `Form`.
  - `ManagerFormField` renders one field and `ManagerFormFields` a list of them. A form with fields of
    its own renders field by field in its own order, calling `ManagerFormField` for the generic ones;
    there is no custom type with a render function.
  - The CMS form renders each field in the config's order (D28) through `ManagerFormField`, a date and
    a media field included (D31). What belongs to one field - the slug lock, the taken-value
    suggestion - shows under it.
  - Rejected: dropping `ManagerFields` and rendering every CMS field through `Form.Field` (the component
    serves forms in other plugins and projects; user, 2026-11-11); `ManagerFields` first and the other
    kinds after it (the form loses the config's order).
- **D31. A form toolkit in `src/admin/components/`, apart from the CMS (user, 2026-11-11).** What builds
  a form's content - `ManagerFormFields` with every field type, the media components,
  `StackedModalShell`, `ChipInput` - lives in `src/admin/components/` and imports nothing of the CMS:
  not `src/lib/`, `src/api/`, `src/workflows/`, `src/admin/cms/` or `src/admin/hooks/api/`, which a lint
  rule refuses. It is the base other plugins take. It stays in this plugin until a second plugin uses
  it, and then becomes a package, a production dependency decided at that point.
  - It holds a form's content only: its fields, their inputs and their layout - the sections, rows,
    groups, collapsibles, tabs and component nodes `FormLayout` draws them in, each through a renderer
    the form gives. The container, the schema, the default values and the save stay with the form.
  - `ManagerFormField` renders a `date` with `DatePicker` and a `media` field with the picker for one
    file or the list for several.
  - A media field learns where its files come from through a `MediaSource` the form hands to
    `MediaFieldsProvider`: the upload limit, whether the library can be searched, its page size, and
    the hook that reads one page. Its records are `MediaRecord`s (`id`, `url`, `filename`, `mime_type`,
    `size`, `thumbnail_url`). The form keeps the records and the chosen files with
    `useMediaRecordStore`, and uploads the files in its own save with `usePendingMediaUpload`, given
    the upload. The CMS's source reads `GET /admin/cms/media`, and its upload is `POST /admin/cms/media`.
  - `sectionFormFields` is an add-on: it lays named items out in sections, in the `main` or the `side`
    column. The columns are Medusa's `LayoutComposer`, and how a section looks is the form's.
  - Its copy sits under one top-level key, `managerFormFields`, shared by every plugin that ships the
    toolkit, not under `cms`: the same texts merge into Medusa's one namespace, and one version of the
    toolkit keeps them the same.
  - A `blocks` field - a list of typed items, each with its own fields - comes with 1d, for areas and
    repeaters alike (D32).
  - Rejected: a save pipeline in the toolkit (a save differs from form to form; user, 2026-11-11); a
    sections component that renders the cards (Medusa lays the columns out; user, 2026-11-11); a
    package now (one consumer).
- **D32. Repeaters are a block's areas, and their items are blocks (user, 2026-11-12).** A block's
  repeated items can differ: a grid holds cards and images, each type with its own fields. So a block
  has `repeaters` - areas inside it, configured as an area is (`label`, `blocks`, `minRows`, `maxRows`) -
  and each item is a block of a type the repeater lists. A repeater of one type is the plain repeated row.
  `repeaters` replaces both of a block's earlier keys, `lists` and `areas`; a collection keeps `areas`.
  - One `blocks` list in the config: no separate kind of block for repeaters. Where a type may go is what
    each area's or repeater's `blocks` lists, so a type meant for a grid's items never reaches a page's
    sections unless they list it, and a type may serve both.
  - Repeaters stay on blocks: a document that needs repeated items gets a block with a repeater in one of
    its areas, not a repeater of its own. Blocks are what makes a document's content open-ended.
  - Storage and reads are those of areas (D4, D26): the area model with `parent_id` set to the block, one
    table per block type. The planned Admin is unchanged.
  - Rejected: `lists`, rows of one child model per block (a second mechanism next to areas, one shape per
    list); a repeater of fixed rows alongside a repeater of blocks (two ways to the same result); repeater
    UI options - collapsed rows, layouts, button labels - for now (user, 2026-11-12).
  - Amended 2026-11-23 (user): a block's `repeaters` are named `areas`, as a collection's are, since they
    are one mechanism; a block's sections may place its areas, and a block with sections lays out every
    field in them. Storage and reads are unchanged. Detail in
    [sub-block-areas](./2026-11-23-sub-block-areas.md).
- **D33. Where a field's config works (user, 2026-11-12).** Every key of a field belongs to one group,
  and its place in the config says which:

  | Group                              | Keys                                                                                 | Where it works                                                                                                                                                             |
  | ---------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Data rules, plain data, at the top | `type`, `label`, `options`, `from`, `multiple`, `max`                                | The server enforces them on every write; the Admin gets them in the projection and mirrors them for the editor - a required mark, a fourth option disabled.                |
  | Server functions, named `server*`  | `serverValidation` and `serverPublishValidation` (Zod), `serverTransform` (a slug's) | The server only; the Admin shows `serverValidation`'s messages from the validation it asks for while the editor types, and builds a slug itself only with `normalizeSlug`. |
  | Admin code, named                  | `options: { hook }`                                                                  | The host registers the code in its own Admin; the server checks the value's type only.                                                                                     |
  | Editor hints, under `admin`        | `description`, `recommendedLength`, `placeholderFrom`, `lockOnEdit`, `mimeTypes`     | The Admin only; the server never checks a value against them.                                                                                                              |
  - The server is the source of truth: every rule that guards data runs there, and the Admin repeats it
    only to spare the editor a refused save. A hook's values are the one exception, checked as texts.
  - A rule the Admin must act on - disable an option, block an input - is a data rule (`max`); a rule a
    message is enough for is `serverValidation`.
  - The registry still checks the hints when the config is resolved - `placeholderFrom` names another
    text field - as a check of the config, not of a value. The projection stays flat.
  - Rejected: `clientValidation` (no function reaches the Admin, and a rule the server does not hold is
    no rule); the hints at the top beside the data rules (the config does not say they are hints).
  - Amended 2026-11-14 (user): `required` left the data rules. Whether a field must be filled comes from
    its schemas: one whose `serverValidation` refuses an empty value is required at every save, one whose
    `serverPublishValidation` refuses it is required to publish, and a field with neither may stay empty.
    The registry works the word out and the projection carries it as `required: "always" | "publish"`,
    so the Admin still marks a required field and checks it without asking the server
    ([sub-admin-field-components](./ended/2026-11-13-sub-admin-field-components.md), 1b).
  - Amended 2026-11-20 (user): `accept` left the data rules. The server cannot hold a field's file
    types on a save - a stored record need not carry its type, and the upload route knows no field - so
    the picker was the only check. The rule splits by where it holds: the media provider's `mimeTypes`, which the server enforces on upload beside `maxFileSize`, and
    a field's `admin.mimeTypes`, an editor hint narrowing the provider's types in the picker
    ([sub-media-mime-types](./ended/2026-11-20-sub-media-mime-types.md)). Both take `type/*`; a provider
    without `mimeTypes` takes any type.

  - Deferred (user, 2026-11-17): grouping a field type's own settings - `options`, `multiple`, `max`,
    `accept`, `stores`, `from`, `linkPolicy` - in one object of the field, so they read apart from the
    keys every field has. Not now: the field union already keeps each type's keys to that type, the
    top-level place is this decision's rule for a data rule, and doing it for every type is a breaking
    change of every host's config, to be decided in a sub-spec of its own. `url` keeps `linkPolicy` at
    the top level until then.
- **D34. Navigation is a feature of the plugin, not a collection (user, 2026-11-16).** A store's menus -
  a header, a footer - are the structure of the site, not editorial content, but they point at the
  content the CMS holds and share its editors, its Admin section and its translations. So the plugin
  ships navigation beside its collections, with models, an editor and a store read of its own.
  - **Models.** A menu group with a `handle` the storefront reads it by, a title, an active flag, an
    optional maximum depth and a flag that keeps it from being deleted; its items a tree - a parent and
    children, ordered by a rank - each of a type: a product category or a product collection, linked to
    Medusa's own record; a raw URL; a heading that links nowhere; or a **page**, a CMS document picked in
    the Admin.
  - **Store read.** One menu by its handle, its items as a tree. A category or collection item takes its
    record's name unless it has a label of its own. A page item gets the page's URL in the request's
    locale, so a menu follows a page's slug in every language and a renamed slug breaks no menu. An item
    whose target is inactive, unpublished or deleted is left out.
  - **Admin.** A tree editor under **Content**: add, nest, reorder, remove, and a picker for each
    target type. Not the document form: a tree reordered by dragging is another editor, and its rules -
    depth, protected groups, pruned targets - would be exceptions in a collection.
  - **Translations.** Item labels are `.translatable()`, edited where Medusa edits every translation.
  - **Generic.** The plugin names no menu: a project creates its groups - `header`, `footer` - by its
    config or a seed, and protects the ones its storefront needs.
  - Rejected: navigation as a collection whose items are blocks nested by repeaters (D32). A menu gains
    little from drafts and versions, and its tree and rules fit a form of blocks badly (user,
    2026-11-16).
  - A project that built menus as a module of its own moves them by a migration script once the plugin
    covers what that module does.
- **D35. A collection bound to a Medusa entity, one document per record (user, 2026-11-16).** A product
  page's sections, a category's banner and text: content that belongs to one commerce record and has no
  address of its own, as the record's handle is its address. Such a collection names the entity and the
  column that holds its id, and the plugin keeps the pair one to one.
  - **No slug.** The document is found by the record's id; the storefront reads the record from Medusa
    by its handle, then the document by that id. A slug is a field the collection may leave out: only
    `status`, `published_at`, `created_by` and `updated_by` are required (D7).
  - **One to one.** The id column is unique in the database, and the Admin offers no picker for it: the
    editor never chooses the record.
  - **Created from the record.** A widget on the record's page in the Admin creates the document, with
    the id set, and opens it; the collection's own list offers no create. In the document's form the id
    shows read-only, with the record's name and a link to it.
  - **The record's lifecycle.** A deleted record takes its document with it, through a subscriber and
    the CMS's own delete workflow.
  - **Store read.** By the record's id, one document with its areas (D10, D20); the record itself stays
    Medusa's, an id only (D9).
  - **Many records at once.** A product listing reads the documents of its products in one request, as
    Medusa's own list routes do (`GET /store/product-variants?product_id[]=...`): the collection's store
    list takes `id` and the record's column (`product_id`) as filters of one value or a list, with no
    `filterable` needed for the record's column, and answers `{ documents, count, limit, offset }` with
    `fields`, `order`, `limit` and `offset` as D20 has them, an area such as `*teaser` included (D10);
    one query, `product_id IN (...)` on its unique index, published documents only. No separate batch
    route, and one `fields` serves a listing and a product page alike (user, 2026-11-16).
  - **Generic.** The entities are Medusa's own - product, product category, product collection - so the
    plugin names no project model. The config key's name is settled in its sub-spec (`boundTo: { entity,
field }` as a working name).
  - **Open, decided in its sub-spec:** whether a document is created when the editor first opens it from
    the record (proposed default, so an import of thousands of products writes nothing) or at the
    record's creation as an option; whether a deleted record deletes or keeps its document; which
    entities come first - products alone, or categories and product collections with them; how the
    collection's list names a document, with no title field of its own.
- **D36. Input safety: refuse at the input, never rewrite text (user, 2026-11-17).** Every value a save
  takes passes the field's checks in `buildDocumentSchema`, the one place the server and the Admin's live
  validation share; the plugin removes nothing from text. Medusa has no such helper in core: queries bind
  values through MikroORM, routes check shapes with Zod, and its one URL check, `safeHttpUrl`
  (`@medusajs/medusa` 2.22.7 `dist/api/utils/common-validators/common.js`), is internal and guards only
  order tracking URLs. A CMS that outputs HTML can sanitise URLs there and store a link's URL nearly as
  typed; this plugin outputs JSON to storefronts it does not control, so it refuses at the input.
  - **SQL** is covered by MikroORM's bound parameters: no escaping of values, and no raw SQL built from
    them.
  - **Control characters:** a text value - `text`, `textarea`, `slug`, a select's or a combobox's value,
    a `text_list` item, rich text - holding `U+0000` is refused at its path; PostgreSQL refuses it in a
    `text` column, which would answer 500. Other control characters are refused too, except tab, line
    feed and carriage return in `textarea` and rich text.
  - **URLs:** a `url` field type on a text column, and rich text's links, check a value against a link
    policy (`protocols`, `relative`), `http`, `https`, `mailto` and `tel` with relative URLs by default.
    A `url` field takes the config's top-level `linkPolicy`, or its own over it; rich text sets its own
    in its link feature, `LinkFeature({ linkPolicy })`, over the default and not over the config's, and
    a policy for every rich text field goes in `richText.features` (amended 2026-11-20, user,
    [sub-rich-text-features](./ended/2026-11-20-sub-rich-text-features.md)). A relative URL starts with `/`, `#` or `?`;
    `//host`, a URL with a space or a control character, and any other scheme, `javascript:` and
    `data:` included, are refused. A URL kept in a plain `text` field is not checked: a host moves it to
    `url`.
  - **HTML** is not removed from text: `a < b` is content. Text is escaped where it is shown - React in
    the Admin, the storefront's renderer - and the package exports `sanitizeUrl`, the same policy as a
    function that answers `#` for a refused URL, for a renderer to apply to stored links, so a URL saved
    before a policy narrowed is safe too.
  - **Rich text** keeps only the nodes and formats of its field's features ([sub-rich-text](./2026-11-17-sub-rich-text.md)),
    and refuses an unknown node.
- **D37. Singletons and nesting in the Admin (user, 2026-11-18).** A collection may be a singleton,
  `singleton: true` with `drafts: false`: at most one document, never deleted, no areas, shown in the
  Admin as independent cards, one per form section, each with its own **Edit** drawer, and a widget zone
  for a host's own cards. A collection may name an `admin.parent`: it leaves the **Content** list and shows
  under its parent - a header button of a list collection's table, a table section on a singleton's page.
  Both are Admin placement and one-document rules over an ordinary collection: the same model rules,
  fields, workflows, routes and store API, rather than a separate globals path. Areas stay for content
  (D4). Detail in [sub-singletons](./ended/2026-11-18-sub-singletons.md).
  - Amended 2026-11-22 (user): `admin.parent` gives way to one `admin.structure` at the config's root,
    which holds in one place the **Content** list, the nesting and each page's entries, filtered
    tables among them, generated from the collections when left out. A host adds to a CMS page with
    Medusa's widgets. Detail in [sub-admin-building-blocks](./2026-11-22-sub-admin-building-blocks.md);
    `parent` stays until its Phase 2.
  - Amended 2026-11-24: `admin.parent` removed in 2b of `sub-admin-building-blocks`; a collection is a
    node of `admin.structure`, with a page of its own, or a `table` entry of another page, and its rows
    open their page or a drawer as its `admin.edit` says.
  - Amended 2026-11-24 (user): `admin.routes` replaces `admin.structure` in 2f of
    `sub-admin-building-blocks`. A route has a `slug`, its page's address `/cms/<slug>`, and the
    collection its page shows; the tree's top level is **Content**, in its order. A collection is on one
    route at most, or in a singleton's `table` section, which 2e put in the collection's
    `admin.sections` in place of a node's page entries; a collection on no route has no page and no
    address.
  - Amended 2026-11-24 (user): a route shows `collections`, always a list, one or several, each drawn
    as its kind does, in place of a separate view kind (2g). A document stands at
    `/cms/<route>/<collection>/<id>`, and every route's page shares one widget zone,
    `cms.route.details`.
- **D38. Events: created, updated, deleted (user, 2026-11-18).** One event per write, named as Medusa names
  its own: `cms.document.created` `{ collection, id, status }`, `cms.document.updated` `{ collection, id,
  action, status }` with `action` `save`, `publish`, `unpublish`, `restore` or `discard`, and
  `cms.document.deleted` `{ collection, id }`. A save in a collection without drafts, a singleton's
  included, is `publish`: it changes what the store serves. A subscriber - a storefront's revalidation -
  reads that from the event alone, whatever the collection's config. Facts only, no snapshot of the
  content; a field such as the slug may be added later. Replaces `cms.document.published` and
  `unpublished`; the plugin is not published yet, so no bridge is kept (user, 2026-11-18). Detail in `sub-collections-and-documents`, Events.
- **D39. The config's Admin texts are keys of one namespace, when it names one (user, 2026-11-20).**
  `admin: { translationNs }` in the config makes every text it gives the Admin a key in that i18next
  namespace, translated by the host's `src/admin/i18n/index.ts`, as Medusa treats a route's `label` and
  `translationNs`; without it, the texts are plain. The Admin translates the collection list where it
  enters, so the form toolkit stays generic (D31). Server messages an editor sees quote no config label.
  Content in other languages stays `sub-cms-translations`. Detail in
  [sub-admin-text-translations](./ended/2026-11-20-sub-admin-text-translations.md). Its texts-as-keys give way

- **D40. A config value is a value or a function of one params object (user, 2026-11-20).** A key that
  opts in takes `ConfigValue<TValue, TParams>`: a value, or a function run once on the server at start,
  whose result the registry keeps. Every function takes one object, so a later parameter breaks none:
  `features` takes `{ defaultFeatures }` and `admin.actions` `{ defaultActions }`, the defaults named after
  the key. A text is a string, shown as written, or a function given `{ t }`, whose `t` names a translation the Admin resolves in the editor's language. Admin code is
  still named in the config and registered in the Admin, as `options: { hook }`. Detail in
  [sub-config-value-functions](./ended/2026-11-20-sub-config-value-functions.md).
  - Amended 2026-11-20 (user): a `richtext` field's `features` takes
    `{ defaultFeatures, rootFeatures }` - the built-in features and the config's `richText.features` - and
    the config's `richText.features` takes a function of `{ defaultFeatures }` too. Detail in
    [sub-rich-text-features](./ended/2026-11-20-sub-rich-text-features.md).
- **D41. The CMS's Admin is the plugin's: the config fills it, a host adds to it (user, 2026-11-22).**
  Medusa lets a host add widgets to its pages, while the dashboard's own sections stay its own: it builds
  its views its way, and the rest adapts. The CMS is a layer of its own and takes the same stance on its
  pages.
  - **A CMS's layout, for content.** The screens edit content: pages, posts, settings, menus. The plugin
    builds no Admin screen for anything else; products, orders and the rest of the commerce keep
    Medusa's own. Where content belongs to a Medusa record (D35), the CMS's blocks show it beside the
    record's screen and neither build nor replace that screen.
  - **The config says what a page or a form holds and how it is grouped; how it is drawn is the
    plugin's**, the same in every project. A collection's add and edit forms always look like the
    CMS's form, whether they open over a page or fill it.
  - **A host adds, never removes or replaces.** Its cards are Medusa widgets in the CMS's zones; one
    value in a table is a field's `Cell`, one input in a form a component node. A different drawing is a
    page of the host's own, built from the plugin's exported blocks. Replacing a whole
    list or edit view is left out.
  - **Every write stays the plugin's.** The server checks every save, whatever sent it, and a form's
    state, checks and save stay in the plugin's form, whatever draws around it.
  - **The config orders a page; an editor arranges only widgets** (user, 2026-11-22). The dashboard's
    `LayoutComposer` makes an entry an editor moves and hides of every element a page puts in it, so the
    CMS draws its pages in a layout of its own, made with Medusa's `defineLayoutConfig`, which draws the
    CMS's blocks itself and leaves its columns' widgets to the editor. Widgets are moved and hidden as on
    any Medusa page. The fallbacks, should the layout fail its gate, are in
    [sub-admin-building-blocks](./2026-11-22-sub-admin-building-blocks.md), "Order on a page".

  | The plugin's, fixed | Open to the config | Open to a host's code |
  |---|---|---|
  | The **Content** page, `/cms`, and its table of collections | Which collections it lists, in which order | - |
  | A list page's own table: its header, **Create**, search, the status filter, pages, row links | Its columns (`admin.table`), how its rows are edited (`admin.edit`), its header buttons (`actions`), the tables after it | A widget in the list's zone; a field's `Cell` |
  | A singleton's page: a card per section, each with **Edit** | The cards' order and column, the tables after them | A widget in the singleton's zone; a field's `Cell` |
  | A table: order, pages, URL state, row actions, deletes | Its collection, label, filter, columns and their cells | A field's `Cell` |
  | The document page: its header with **Save**, the status, the history, the version view, the stale-version alert | The form's fields and sections | A widget in the document's zone; a field's component node |
  | The add and edit forms: their modal or drawer, header and footer, how a section, a tab, a row and each field type look, state, checks, media, uploads and save | Which fields, in which sections, tabs and rows, with which validation | A field's component node, an options hook |
  | Routes, breadcrumbs, the writes and their checks | The nesting | A `validate` hook on the server |

  The config's keys for the nesting, the pages and their tables, the widget zones and the cell are in
  [sub-admin-building-blocks](./2026-11-22-sub-admin-building-blocks.md).

## Scope

### In scope

- The plugin: config, DML introspection, registry, area reads and writes, validation, generic
  workflows, Admin and store API, Admin **Content** screens.
- Later sub-specs: versions, a draft read for preview, a publish schedule, translations, permissions,
  navigation (D34), validation messages in the editor's language - the plugin's and a host's Zod
  messages (user, 2026-11-20).

### Out of scope

- A host project's content models, config and links (D2, D6); any storefront code (D17).
- Translated content in the store API until `sub-cms-translations`, behind Medusa's `translation` flag.
- Permissions in the first versions (D12); live preview, document locking, autosave, polymorphic
  references.
- Generic JSON columns as editable content (D3).
- Admin screens for anything but content, and a host's replacement of the CMS's own views (D41).

## Architecture

```
@mostrajs/cms
  src/lib/            defineConfig, DML introspection, registry, area reads and writes,
                      client projection, validation schema builder,
                      AbstractCmsMediaProvider and FileMediaProvider (D29)
  src/modules/cms/    holds the config from the plugin options; no models yet
  src/workflows/cms/  list, get, create, update, publish, unpublish, delete; media upload and search
  src/api/admin/cms/  collections, documents, reference search, media upload and search
  src/api/store/cms/  published documents; fields, order and declared filters
  src/admin/          Content: collections, documents, generated edit form, media picker

host project
  src/modules/content/   models, a plain MedusaService, migrations generated by the user (D2)
  src/cms/config.ts      registers collections and blocks (D6), and a media provider of its own (D29)
  medusa-config.ts       registers the module and the plugin with its options, and the File Module's
                         file provider (S3, local) as for any Medusa project
```

`src/lib/` is two layers (user, 2026-11-21). The config layer turns the project's config and its models
into the registry: `media-provider/`, `config/`, `model/`, `field/`, `layout/`, `area/`, `block/`,
`collection/`, `media/` and `registry/`, in that order. The read layer, `document/`, reads and writes
documents with a built registry, and `cache/` after it names a collection's cache tags. A folder imports
only the folders before it in this order - never one after it, not even through a third folder - and a
new folder takes its place in the order when it is added. The check is in
[sub-lib-structure-review](./ended/2026-11-21-sub-lib-structure-review.md), "Acceptance Criteria".

```
content_page ─────< content_area >── content_block_hero
content_blog_post ─<      │       >── content_block_grid ──< content_block_grid_item
                          │       >── ... one model per block type
   (FK page_id / blog_post_id, CHECK one set, parent_id)   (FK area_id, rank)   (FK grid_id, rank)

content_blog_post >──< content_blog_category     (pivot, no areas)
content_blog_post >──< content_blog_tag          (pivot, no areas)
```

Data flow for an edit: the Admin reads the collection projection (`GET /admin/cms/collections`), renders
the document form with its areas, validates locally and posts the document with its areas. The plugin's
workflow validates, prepares a write that updates what it was sent, creates what is new and soft-deletes
what is gone (D27), and applies it through the project's generated service methods, with Medusa's
compensation; it clears the cache tags of every written record. A store read parses `fields`, `order` and
the declared filters against the registry, through Medusa's `validateAndTransformQuery`, and runs one of
two exported workflows, `get-published-cms-document` or `list-published-cms-documents`, which read
through the cache by default; the Admin's reads never do (user, 2026-11-18). A read with areas is one `query.graph` on the collection with
`areas.*`, each block relation and each list relation; the plugin builds the tree, orders blocks by
`rank`, adds `block_type`, populates the requested CMS relations, reads every media record through
the media provider's `retrieve` in one call (D29), and removes system columns. The
workflows emit `cms.document.created`, `updated` and `deleted` for any consumer (D38).

### Alternatives considered

- **A self-hosted CMS as a separate app, or in its own schema of the Medusa database.** A second
  application, or another CMS's migrations run against the Medusa database. Rejected.
- **A hosted CMS.** A second Admin and login, content with a third party, and no Medusa translations.
  Above all, it sits outside Medusa's workflows, events, cache and visibility rules. Rejected.
- **Visibility as a plugin concept** - audience dimensions the plugin resolves from the request and
  enforces in the store API. Rejected by the user for plain option fields (D18): the plugin stays
  storefront-agnostic (D17) and the store API public.
- **A separate homepage collection.** One more model and a second way of doing what a page does.
  Rejected by the user; how a collection's settings name its homepage is specified next (D21).
- **A dedicated route per filtered read.** Rejected by the user: the list route with declared filters
  and `fields` serves any such read (D20).
- **Models generated by the CMS from a field config** (the first draft). A second modelling language
  next to DML. Rejected by the user (D2).
- **Block content as JSON**, in the document or in one shared block table. Rejected by the user: Medusa
  translations and filters need columns (D3).
- **Variants A and C of block ownership.** See D4.
- **One table per collection and block type.** Foreign keys without an area model,
  but a hand-written model for every collection x block pair (30 for 3 x 10). Rejected for D4.
